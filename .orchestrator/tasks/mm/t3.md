# Chat UI: audio attachments

## Goal
Let the `/chat` page attach and send audio files as OpenAI-standard `input_audio`
content parts.

## Why
The Chat page is the de-facto playground and already handles images, video files,
and YouTube links — but has no audio path at all (`accept` filters are
`image/*` and `video/*` only). Gemma-4 understands audio natively.

## What to build
1. Attach-menu entry "Audio" with a hidden `<input accept="audio/*">`; extend
   drag-drop and paste classification to accept audio files.
2. An audio `AttachmentChip` variant showing filename + duration (`MM:SS`), reusing
   the existing uploading/error/retry/remove affordances.
3. `buildMessageContent()` emits standard parts:
   `{ type:'input_audio', input_audio:{ data:'<base64>', format:'wav'|'mp3' } }`.
   Note this is base64 **without** a `data:` URI prefix — unlike `image_url`.
   Precede it with a `[audio: <name>, duration MM:SS]` text marker, mirroring the
   existing `[video: …]` / `[frame n/N @ MM:SS]` convention.
4. Route audio through the existing `ingestMedia` flow so long files are handled
   server-side rather than inlined blindly.

## Public surface changes
`buildMessageContent` can now emit `input_audio` parts. New chip variant.

## Acceptance criteria
- [ ] Attaching a WAV and an MP3 produces a correctly shaped `input_audio` part
      (assert against `buildMessageContent` directly).
- [ ] Existing image / video / YouTube / long-text paths are unchanged — verify the
      existing behaviours still produce identical part arrays.
- [ ] Chip shows duration and supports remove/retry.
- [ ] `./scripts/dev-build.sh check` and `container` pass.

## Out of scope
Microphone recording (explicitly excluded). Sampling-param UI. The API Docs page.
