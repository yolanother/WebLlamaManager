# OpenAI-compatible /v1/audio/transcriptions

## Goal
Implement `POST /v1/audio/transcriptions` (and `/api/v1/audio/transcriptions`)
backed by Gemma-4's native audio encoder.

## Why
No `/v1/audio/*` route of any kind exists. Adding the standard STT endpoint lets
existing OpenAI STT clients work against this box unmodified, which is the stated
primary goal (OpenAI compatibility).

## Depends on
The capability-metadata task (shares `api/server.js`; land after it and rebase).

## What to build
Accept multipart: `file` (required), `model`, `response_format`
(`json` | `text` | `verbose_json`, default `json`), optional `language`, `prompt`.

- Normalise the upload through `extractAudio` (16 kHz mono WAV).
- Segment long audio with `planSegments`, transcribe each window via a chat
  completion carrying an `input_audio` part and a transcription instruction, then
  concatenate.
- `json` → `{ text }`. `text` → `text/plain` body. `verbose_json` → `{ task,
  language, duration, text, segments[] }` where segment boundaries come from **our
  windowing**.
- **Document plainly, in the response docs and the code header, that `verbose_json`
  segment timings are approximate**: Gemma is not a dedicated ASR model and the
  boundaries are our window edges, not detected speech boundaries. Do not imply
  word-level accuracy.
- Reject a model without audio capability with a clear 4xx naming the reason.

## Public surface changes
`POST /v1/audio/transcriptions` and `POST /api/v1/audio/transcriptions`.

## Acceptance criteria
- [ ] Tests (injected fakes) cover all three `response_format` values, a
      multi-window file, a missing `file` (400), and a non-audio model (4xx).
- [ ] An OpenAI Python client's `audio.transcriptions.create(...)` shape is accepted.
- [ ] `./scripts/dev-build.sh check` and `container` pass.

## Out of scope
`/v1/audio/speech` (TTS) — explicitly excluded. Word-level timestamps. Diarization.
