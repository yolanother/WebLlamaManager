# Model capability metadata, multimodal routing, and token accounting

## Goal
Replace the regex-based vision guess with real capability metadata read from mmproj
GGUF headers, expose it on `/v1/models`, route audio requests to audio-capable
models, and stop counting multimodal parts as zero tokens.

## Why
Vision capability is currently inferred from a regex on the model id
(`api/chat-router.js:17` — `/vl|vision|llava|gemma|qwen.*vl|minicpm/i`). There is no
audio equivalent at all, and `/v1/models` exposes no modality field, so an agent
cannot discover what a model can accept. Separately `estimateInputTokens`
(`api/server.js:671-679`) counts only `type === 'text'` parts, so images and audio
cost **zero** in queue admission and remote-offload sizing — which will misbehave
badly once multimodal traffic is routine.

- Design doc §5.3.

## What to build
1. `api/model-capabilities.js`: locate `mmproj*.gguf` beside each model in the models
   dir, parse the GGUF header key-values, return `{ vision: bool, audio: bool }`.
   **Cache** — this must not run per request. Parse the GGUF header directly; do not
   add an npm dependency.
2. `GET /v1/models` entries gain `modalities: ["text","image","audio"]` reflecting
   real capability.
3. `chat-router.js`: real metadata wins; keep `VISION_MODEL_PATTERN` only as a
   fallback when no mmproj is found. Extend `attachmentPresence()` to detect
   `input_audio` / `audio_url`, and extend `filterRoutingCandidates()` to restrict
   audio-bearing auto-routed requests to audio-capable models. Add
   `config.routerAudioModels` as the operator override, mirroring `routerVisionModels`.
4. `estimateInputTokens`: charge a documented non-zero estimate per image part and
   per second of audio. Approximate is fine; zero is not. Put the constants in one
   named place with a comment explaining the derivation.

## Public surface changes

- New module `api/model-capabilities.js`.
