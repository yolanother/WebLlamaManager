# Live-USB appliance mode

Copyright (c) 2026 DoubTech. Use of this document is governed by the LICENSE
file in the repository root.

The Llama Manager ISO boots into a **fully functional live appliance** straight
from the USB stick: the kiosk dashboard comes up and works (model performance is
constrained by live-media speed), with a prominent **Install to disk** entry
point that launches the existing guided install flow. Installing is now an
explicit user choice made from inside the running live appliance — the ISO no
longer boots straight into the installer.

## Boot menu

`scripts/build-iso.sh` injects a GRUB menu generated by
`scripts/generate-grub-config.sh` in place of the upstream menu:

| Entry | Default | Kernel command line (essentials) | Effect |
|-------|:------:|----------------------------------|--------|
| **Try Llama Manager (live appliance)** | ✅ | `boot=casper ds=nocloud;s=/cdrom/llama-manager/live/` | Live session; appliance autostarts from media. No installer. |
| **Install Llama Manager (guided)** | | `boot=casper autoinstall ds=nocloud;s=/cdrom/llama-manager/autoinstall/` | Runs the offline autoinstall flow. |
| **Try Llama Manager (safe graphics)** | | live command line + `nomodeset` | Live session on systems that need `nomodeset`. |

The NoCloud datasource semicolon is escaped as `\;` in the generated `grub.cfg`
so GRUB passes it to the kernel command line instead of treating it as a command
separator. Only the guided-install entry carries the `autoinstall` trigger, so
the default boot never starts the installer.

## Media layout

Everything the live session and the installer need is assembled into the
`/llama-manager` payload by `scripts/assemble-iso-payload.sh` and mapped onto the
ISO by `scripts/build-iso.sh`:

```
/boot/grub/grub.cfg                       generated appliance boot menu
/llama-manager/install-offline.sh         offline installer (disk installs only)
/llama-manager/apt, bootstrap, assets     signed repo, archive key, Qwen model
/llama-manager/live/                       live-session customization
  start-live-appliance.sh                  live autostart orchestrator
  install-to-disk.sh                       install-to-disk handler (a.k.a. live-install)
  llama-manager-live.service               autostart systemd unit
  llama-manager-install.desktop            "Install to disk" launcher
  user-data / meta-data                    cloud-init NoCloud seed for the live session
/llama-manager/autoinstall/                guided-install autoinstall seed
  user-data                                the unchanged autoinstall.yaml profile
  meta-data                                NoCloud meta-data
```

## Live-session startup (the appliance is already in the squashfs)

The appliance is **baked into the casper live layer at build time** by
`scripts/customize-live-filesystem.sh` — the same stage that brands the layer —
so a live boot **installs nothing**. See
[BUILDING.md](BUILDING.md#the-appliance-stack-is-baked-into-the-live-layer) for
what goes in and how.

1. The live GRUB entry seeds `ds=nocloud;s=/cdrom/llama-manager/live/`.
2. `live/user-data` (`runcmd`) copies `llama-manager-live.service` into
   `/etc/systemd/system`, reloads systemd, and starts it.
3. The unit runs `/cdrom/llama-manager/live/start-live-appliance.sh`, which:
   - publishes the dashboard hooks (see below);
   - places the `live-install` handler on `PATH` and drops the desktop launcher;
   - **suppresses Ubuntu's own installer** (see below) before anything slow runs;
   - brings up the branded kiosk shell;
   - **starts** the pre-baked `llama-manager.service` — the unit is already
     enabled inside the layer, so systemd usually has it up before this runs and
     the explicit start only makes the ordering deterministic;
   - creates the engine container around the pre-populated, read-only Podman
     image store, last, so the dashboard and kiosk remain available first.

### Live mode used to install a lean package set, and that is what broke

Live mode deliberately skipped `llama-manager-appliance`, because that
meta-package pulls `linux-image-unsigned-6.18.36`, `linux-modules-6.18.36`,
`podman`, `distrobox`, `initramfs-tools`, `kmod`, `mokutil`, `nfs-common` and
`uidmap` — gigabytes of writes into a **RAM-backed casper overlay** — and instead
apt-installed `llama-manager` alone at every boot.

That reasoning is correct about **installing at boot** and wrong as an argument
against **pre-baking at build time**: squashfs pages are read from the USB, not
held in RAM. And the boot-time install was fragile by construction. It failed for
real: the dependency bundle's `curl` could not be installed over the live layer's
`libcurl4t64`, apt aborted, nothing listened on 3001 or 80, and the kiosk sat on
"Setting up from the boot media" forever.

`install-offline.sh` still ships on the media and still takes
`LLAMA_MANAGER_PACKAGES`. The disk install now also carries the narrow mainline
kernel compatibility described in
[BUILDING.md](BUILDING.md#the-pinned-mainline-kernel-needs-a-run-parts-compatibility-shim),
but the live session no longer calls it.

### The model is mounted at /volumes/models, not staged and not named

`/etc/llama-manager/llama-manager.env` in the live layer sets
`MODELS_DIR=/volumes/models` — and **only** that. `/volumes` is where the
appliance mounts attached storage (NFS on a real deployment), so
`/volumes/models` is the stable, source-agnostic location the engine is
configured for and the only one it ever learns.

The live session bind-mounts the medium's `assets/models` directory onto that
path before starting the service. An installed appliance backs the same path with
NFS or a local disk. **No engine configuration differs between them**, which is
the entire point of the indirection: a raw `/cdrom/...` path in the engine's
config would hardcode the boot medium and have to be undone the moment the models
live anywhere else.

Nothing is copied either way. The Qwen3-8B GGUF is 4.7 GB and the live session's
writable layer is RAM.

Disk installation uses the same canonical engine path without the live bind
mount. The ROCm postinst creates `/volumes` and its service-owned
`/volumes/models` mountpoint, and `install-offline.sh` stages the verified Qwen
file there with mode `0660`. Only after that stage succeeds does it remove the
exact obsolete bundled copy at
`/var/lib/llama-manager/models/Qwen3-8B-Q4_K_M.gguf`; unrelated operator models
remain untouched.

### The engine image is pre-populated for live media

Importing the packaged archive at live boot expanded the rootless store to
31 GB on hardware and exhausted casper's 32 GB RAM overlay. The release build
now creates a read-only Podman `additionalimagestores` tree in the squashfs,
maps it to the `llama-manager` account, and removes the OCI archive from the live
layer. `start-live-appliance.sh` creates only the container's writable metadata,
after the dashboard is up. See
[BUILDING.md](BUILDING.md#the-live-engine-uses-a-pre-populated-image-store).

The installed-system ROCm package has a separate first-boot oneshot that imports
its retained local archive. That oneshot checks
`ConditionPathExists=/usr/lib/llama-manager/offline/llama-rocm-7.2.4.oci.tar`,
so systemd skips it successfully on live media and the manager's required-unit
relationship does not replace this pre-populated live path.

### The live session runs the GPU stack, measured

This document used to say the live session pulled in "a GPU stack the live
session cannot use anyway". **That is false**, and it was the kind of stale claim
that gets working code deleted.

Measured on a booted appliance, on the live media's own casper kernel
(`6.17.0-14-generic` — *not* the pinned mainline `6.18.36`), running
`llama-cli -m /volumes/models/Qwen3-8B-Q4_K_M.gguf -ngl 99` with
`HSA_OVERRIDE_GFX_VERSION=11.5.1` and `/dev/kfd` + `/dev/dri` passed through:

```
Prompt: 185.5 t/s | Generation: 49.4 t/s
```

49 t/s is full-offload GPU speed on this hardware; a CPU-only fallback gives
~10–15 t/s. So `llama-manager-rocm-gfx1151`'s hard dependency on
`linux-image-unsigned-6.18.36` is **deliberately left unsatisfied in the live
layer** — see
[BUILDING.md](BUILDING.md#the-pinned-kernel-dependency-is-not-satisfied-in-the-live-layer).
The pin is untouched for the installed system.

### Suppressing Ubuntu's installer

Ubuntu 24.04's installer is the **`ubuntu-desktop-bootstrap` snap**, not a
package with an autostart file. There is no
`/etc/xdg/autostart/ubuntu-desktop-bootstrap.desktop` to delete — the live layer's
`/etc/xdg/autostart` holds only two `ibus-mozc` entries. What exists is:

- **`/usr/lib/systemd/user/ubuntu-desktop-installer.service`**, enabled through
  `/etc/systemd/user/graphical-session.target.wants/`, with
  `ExecStart=/snap/bin/ubuntu-desktop-bootstrap --try-or-install`. **This is what
  puts the installer on screen** — it is a systemd *user* unit, which is why no
  `/etc/xdg/autostart` entry exists. (Written into the layer by
  `casper-bottom/61desktop_canary_tweaks`; the name still says
  `ubuntu-desktop-installer`, the binary it starts is `ubuntu-desktop-bootstrap`.)
- `snap.ubuntu-desktop-bootstrap.subiquity-server.service`, its subiquity backend,
  plus the snap mount units wired into `multi-user.target.wants` and
  `snapd.mounts.target.wants`;
- `/var/lib/snapd/desktop/applications/ubuntu-desktop-bootstrap_ubuntu-desktop-bootstrap.desktop`,
  snapd's exported launcher;
- a copy of that launcher on the live user's Desktop, placed at boot by casper's
  initrd hook `casper-bottom/25adduser` — and *only* when that exported launcher
  exists.

Casper autologins the live user into a normal GNOME session
(`casper-bottom/15autologin` edits `/etc/gdm3/custom.conf`), so the installer
rides that session — and it rides it **immediately**, well before
`llama-manager-live.service` is ordered to run.

**The race is therefore not winnable at boot, so it is removed at build time.**
`scripts/customize-live-filesystem.sh` takes the installer apart inside the
squashfs, in the same pass that installs the branding:

- drops the `graphical-session.target.wants` link and masks
  `ubuntu-desktop-installer.service` (symlink to `/dev/null`), so the session
  never starts it;
- masks `snap.ubuntu-desktop-bootstrap.subiquity-server.service` and every
  `snap-ubuntu*bootstrap-*.mount`, and drops their enablement links, so the
  installer binary cannot even be mounted;
- deletes snapd's exported launcher, which also takes the Desktop icon away,
  since `25adduser` copies that file only if it is there.

`start-live-appliance.sh` keeps the same suppression as a **fallback** for media
that predates this stage — but a safe one. On such media the installer has
already won the race by the time it runs, and stopping the subiquity backend
*then* is what tore the running Flutter frontend's server away mid-session and
replaced the appliance with `Something went wrong … sudo ubuntu-bug
ubuntu-desktop-bootstrap`. So it first checks (`pgrep -f
ubuntu-desktop-bootstrap`) whether the frontend is on screen: if it is, it
**masks only** — enough to stop anything restarting the installer, never enough
to kill what the operator is looking at — and lets the kiosk shell cover it. If
it is not running, it stops and masks as before.

Removing the desktop copy is not cosmetic. Masking the snap's mount unit makes
the exported launcher *fail* — clicking it reports
`cannot find installed snap "ubuntu-desktop-bootstrap" at revision <n>: missing
file /snap/ubuntu-desktop-bootstrap/<n>/meta/snap.yaml` — so leaving it on the
desktop hands the operator a broken install button. The replacement is
`llama-manager-install.desktop`, installed executable, chowned to the live user,
and marked `metadata::trusted` in that user's session (GNOME refuses to launch an
untrusted desktop file).

The mount unit's name embeds the snap revision
(`snap-ubuntu\x2ddesktop\x2dbootstrap-494.mount` on today's base image), so it is
discovered by glob, never hardcoded — a rebased base image ships a different
revision and a literal name would silently stop matching. The contract test uses
a deliberately different revision so a hardcoded one cannot pass.

**All of this is proven against the pinned base image** —
`ubuntu-24.04.4-desktop-amd64.iso`, casper layer `minimal.standard.live.squashfs`:
the unit names, the snapd-exported launcher path, the
`casper-bottom/25adduser` copy onto the live user's Desktop, and (settling what an
earlier revision of this document recorded as an unidentified trigger) the
`graphical-session.target.wants` → `ubuntu-desktop-installer.service` user unit
that actually launches the GUI.


The desktop session itself is deliberately **left running** — see below.

### The live user is not `ubuntu`

casper derives the live account **and** the hostname from the first word of
`/.disk/info`. The appliance rewrites that file to announce `Llama Manager`, so
the live session runs as `llama@llama`, not `ubuntu@ubuntu`. Every path that
assumed `ubuntu` was silently wrong on our own media: `id -u ubuntu` failed, so
the kiosk was never launched into the running session, and the snap launcher
removal targeted `/home/ubuntu/Desktop`, so Ubuntu's (now broken) install icon
survived.

`start-live-appliance.sh` therefore **discovers** the account: the first passwd
entry with a uid in the ordinary user range and a real login shell, which is
exactly one account in a casper live session and excludes root, the appliance
service accounts, and `nobody`. `LLAMA_LIVE_USER` overrides it for tests and
hand debugging; `LLAMA_LIVE_USER_FALLBACK` (default `ubuntu`) applies only when
the passwd database yields nothing at all.

### The appliance is its own session under Cage

**This is the primary path, and it replaced an earlier one.** The live boot used
to be gdm autologin → GNOME → XDG autostart → `firefox --kiosk`: a browser
painted over a full desktop the appliance does not control. This document
previously recorded that as deliberate, on the grounds that `cage` could not be
used because "gdm already holds DRM master in the autologin session".

That constraint is real, but it only applies to a compositor started **inside** a
running session. gdm holds DRM master until it starts a *user session* — so
registering the kiosk **as** that session hands Cage the seat cleanly. The
appliance now boots into `kiosk/start-kiosk-shell.sh` as its own Wayland session,
with no desktop underneath it.

Three pieces, all on the medium:

| Piece | Role |
|---|---|
| `iso/live/llama-manager-appliance.desktop` | The Wayland session entry. Installed into `usr/share/wayland-sessions/` in the live layer by `scripts/customize-live-filesystem.sh`'s `register_appliance_session`. |
| `iso/live/select-appliance-session.sh` | Points the live account's AccountsService `Session` key at that entry. |
| `iso/live/llama-manager-session.service` | A oneshot, `Before=display-manager.service gdm.service`, that runs the selector. |

**Why the choice is made at boot and not baked into the image.** gdm reads the
session from AccountsService, which is **per account**, and casper does not
create the live account until boot — its name is derived from `/.disk/info`
(above). There is no account to write the choice against at build time, so a
oneshot ordered ahead of the display manager writes it on the running system.
gdm reads it once, at login, which is why the ordering matters.

**Failure stays recoverable.** If the selector does not run, gdm autologins into
the ordinary desktop session and the XDG autostart entry paints the old
browser-over-GNOME kiosk over it. Degraded, still usable, not a black screen.
`start-kiosk-session.sh` is that fallback and is documented as such in its own
header; it still refuses to use a compositor, for the original reason, because it
runs inside a session that already exists.

Consequences worth knowing:

- **The installer stacks on top.** Cage puts new toplevels above what is already
  there, so the guided installer opens over the running kiosk with no window
  management and nothing torn down to make room. See
  [Install to disk](#install-to-disk) and
  [INSTALLER.md](INSTALLER.md#where-the-installer-draws-over-the-kiosk-not-instead-of-it).
- **One agent, not two.** `start-live-appliance.sh` starts `kiosk-agent.py` as
  root so its hooks keep their privileges; the session launcher reuses that
  already-serving agent rather than starting a second, which would bind-fail,
  exit, and take the shell down with it — a black screen caused by the shell
  working correctly twice.
- **`MOZ_ENABLE_WAYLAND` is exported.** Snap Firefox is the only browser in the
  offline bundle and still defaults to X11; under Cage there is no X.
- **Cage runs with `-s`,** so a wedged appliance shell can be escaped to a VT.
  It is the whole session now; there is nothing underneath to fall back to.
- **"Open desktop mode" is real.** `live-desktop` (`iso/live/open-desktop-mode.sh`)
  repoints the session at `ubuntu`, drops the fallback autostart entry, and
  restarts the display manager. The appliance keeps serving throughout. The kiosk
  had always invoked it and nothing had ever installed it, so the button reported
  success and did nothing.

**Not yet verified on hardware:** that Cage takes the seat on the appliance, and
that the Flutter installer renders as a Cage toplevel. Both are empirical and
need the box.

### Bringing up the kiosk shell

The branded appliance shell is staged on the media at `/cdrom/llama-manager/kiosk/`
by `scripts/assemble-iso-payload.sh`. `start-live-appliance.sh` then:

1. starts `kiosk-agent.py`, which serves the shell on `127.0.0.1:8385`;
2. installs `llama-manager-kiosk.desktop` into `/etc/xdg/autostart`, so a
   *fallback* desktop session started afterwards opens the shell by itself;
3. launches `start-kiosk-session.sh` into the already running session as the
   discovered live user, for the same fallback case — gdm has usually autologged
   in before this script runs and the autostart entry alone would not fire until
   the next session.

Steps 2 and 3 are the fallback layer described above; on a medium where the
appliance session was selected, the shell is already on screen as that session
and the agent started in step 1 is the one it reuses.

This happens **before** the offline appliance install, not after. That install
pulls packages and copies a multi-gigabyte model into a RAM-backed casper
overlay; running it first left the operator staring at a bare GNOME desktop for
its whole duration, and any failure inside it aborted the script before the shell
was ever started. The install is now non-fatal for the same reason: the shell is
the only thing on screen and degrades to reporting the engine as absent, whereas
aborting would leave exactly the desktop this script exists to replace.

**The lean package set does not grow to support the kiosk.** Firefox is present
on the base image — `/snap/bin/firefox` and `snap-firefox-7766.mount` live in
`minimal.squashfs`, with the blob at `/var/lib/snapd/snaps/firefox_7766.snap`.
(The installer-snap suppression globs `snap-ubuntu*bootstrap-*.mount` and so
never touches Firefox's mount unit.) `cage` is already a dependency of
`llama-manager-appliance`.

**Every failure path leaves a usable desktop**, because a desktop is recoverable
and a black screen on first boot is not. Media with no kiosk bundle, a failed
agent, a missing live user, and a missing browser are each a diagnostic on stderr
and nothing more — none of them abort the live session script or tear down the
desktop. If the agent never answers, no browser is launched at all rather than
putting a connection-error page on screen.

**Alternative delivery.** If cloud-init is unavailable or disabled in a given
base image, the same unit and scripts also work when shipped as an additional
casper squashfs layer or enabled by any other live customization; only the
delivery glue in `live/user-data` changes. The scripts are delivery-agnostic and
fully path-overridable via `LLAMA_*` environment variables (see the file
headers), which is how the tests exercise them without a real ISO.

## Install to disk

The visible, kiosk-accessible entry point is `llama-manager-install.desktop`
(`Exec=pkexec live-install`). `live-install` is `iso/live/install-to-disk.sh`,
which:

1. verifies the on-media autoinstall seed
   (`/cdrom/llama-manager/autoinstall/user-data`);
2. hands off to the guided Ubuntu Desktop installer with that seed so the
   installed system uses the identical, unchanged offline autoinstall path,
   launching the GUI **as the live desktop user** with that session's own
   `DISPLAY` / `WAYLAND_DISPLAY` / `XDG_RUNTIME_DIR` read out of the running
   compositor's environment.

**Nothing is torn down.** This handler used to stop `llama-manager-live.service`
and `llama-manager.service` first. Nothing about installing to a disk requires
it: the engine reads its model from read-only media and the installer partitions
a different device, so they do not contend. The teardown was pure downside — it
killed the working shell *before* the installer appeared, so any failure to
launch left the operator on an empty desktop with no way back, which is exactly
what happened when the GUI could not open a window. The appliance now keeps
running and the installer opens on top of it (see
[The appliance is its own session under Cage](#the-appliance-is-its-own-session-under-cage)).
`LLAMA_STOP_LIVE_SERVICES` restores the old behaviour for anyone who wants it;
nothing stops by default.

**The compositor is found by role, not by name.** `install-to-disk.sh` probes
`cage` then `gnome-shell` (`LLAMA_COMPOSITORS`) to locate the session that will
own the installer's window. Looking only for `gnome-shell` found nothing under
the appliance session and handed the installer a guessed `DISPLAY` belonging to
no session at all. Running the Flutter installer as root with no display brings
up the subiquity server and then dies without ever opening a window.

The installer binary and its arguments are overridable so the exact invocation
can be validated in a VM without editing the handler:

- `LLAMA_INSTALLER` — installer binary (default: first of
  `ubuntu-desktop-bootstrap`, `ubuntu-desktop-installer`, `ubiquity` on `PATH`).
- `LLAMA_INSTALLER_ARGS` — extra arguments, e.g.
  `--autoinstall "$LLAMA_AUTOINSTALL_SEED/user-data"`.
- `LLAMA_AUTOINSTALL_SEED` — seed directory (exported to the installer).

The handler is intentionally frontend-agnostic; confirm the precise installer
flag during VM validation. The **"Install Llama Manager (guided)"** boot-menu
entry always provides the same seeded install as a fallback path.

### ROCm initialization waits for the installed system

During the guided install, curtin runs package configuration inside `/target`
while the live session's `/run` is bound into that chroot. Its
`/run/llama-manager` can belong to the live account's different numeric UID,
and rootless Podman's user-namespace clone is not reliable in this incomplete
boot environment. The ROCm maintainer script therefore performs archive and
host-policy setup—including the archive presence check, subordinate IDs,
tmpfiles, the root-owned `/volumes` directory, the service-owned
`/volumes/models` mountpoint, initramfs, and GRUB—but executes no Podman or
Distrobox command.

On the first real disk boot, `llama-manager-rocm-setup.service` receives a fresh
`/run/llama-manager` from systemd and runs the package's offline helper as
`llama-manager`. The manager has a vendor `Requires=`/`After=` gate on this
oneshot, so an image-ID or container-creation failure blocks manager startup.
The unit first requires the `/var/lib/llama-manager` and `/volumes` mounts. Its
helper loads only an absent pinned image reference and creates only a missing
`llama-rocm-7.2.4` container with `/volumes:/volumes`; rerunning it validates
the exact image ID and container name without repeating either operation.
Removal stops the manager first, cleans the package-owned Distrobox and Podman
image while the setup unit still provides `/run/llama-manager`, and stops the
setup unit's completed `RemainAfterExit` state last.

**Branding the installer's own screens** — its theme, page illustrations, the
Ubuntu logo on the language page, and the slideshow — is a separate seam,
documented in [INSTALLER.md](INSTALLER.md).

## Dashboard hooks (for the main app repo — not modified here)

The live session exposes two documented hooks the kiosk dashboard can probe to
surface its own in-dashboard "Install to disk" button:

- **`/run/llama-manager/live-media`** — present only in live mode; its contents
  are the media payload root (e.g. `/cdrom/llama-manager`).
- **`live-install`** — an executable on `PATH` that runs the install-to-disk
  handler. Invoke it (via `pkexec`) to start the guided install.

Wiring these into the dashboard UI is out of scope for this repo; the hooks are
the contract.

## Testing live mode in a VM

Live boot and the appliance install cannot run in the build container; the unit
and config-generation tests are the in-repo acceptance bar. After building an
ISO, validate the full flow in a VM (QEMU/KVM shown; use UEFI and legacy runs):

```bash
qemu-system-x86_64 -enable-kvm -m 8192 -smp 4 \
  -drive file=/path/to/llama-manager-ubuntu-24.04.4.<build>-amd64.iso,media=cdrom \
  -drive file=/tmp/target.qcow2,if=virtio \
  -bios /usr/share/OVMF/OVMF_CODE.fd -net none
```

Verify, offline (`-net none`):

1. The default GRUB entry boots the **live appliance** (no installer), and the
   kiosk dashboard comes up.
2. `/run/llama-manager/live-media` exists and `live-install` is on `PATH`.
3. The desktop launcher / `live-install` stops the live services and launches
   the guided installer against the media seed (confirm the exact
   `LLAMA_INSTALLER_ARGS` flag for the shipped installer here).
4. The **"Install Llama Manager (guided)"** entry still performs the unchanged
   interactive-then-offline install.
